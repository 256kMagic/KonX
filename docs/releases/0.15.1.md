# KonX 0.15.1 — SSH compatibility and console logging

2026-10-22. Save console output with a visible logging switch, connect to more SSH 2 devices, and use more private-key formats with clearer login failures. The recent-history and credential controls from 0.15.0 remain available.

## Features and fixes

- Use **Log to text file** above each SSH, Telnet, raw TCP, or serial console. The switch lights green only after the log file opens successfully, shows its path, and offers **Show log in folder**. State follows that console's backend across tabs, layouts, failures, and disconnects; pending actions are disabled.
- Generate unique `.txt` log filenames in the configured log folder while preserving explicit saved templates. Record new console output until stopped or disconnected. Existing right-click and automatic session logging controls remain available. See [Session logging](../USER_GUIDE.md#session-logging).
- Choose **Automatic — modern preferred, legacy allowed** or **Modern transport only** under a saved session's **Connection → SSH transport compatibility**. Automatic is the default for new sessions and existing sessions without a setting. Invalid stored values require an explicit choice.
- Apply the same transport policy to SSH terminals, standalone SFTP, jump hosts, and SSH audits. Each jump uses its own saved setting; SFTP opened from an existing terminal reuses that connection. Terminal status and audit reports identify negotiated legacy algorithms.
- Load OpenSSH, traditional PEM, PKCS#8, and PuTTY PPK v2/v3 private keys. Support includes RSA, ECDSA NIST P-256/P-384/P-521, and Ed25519, with supported encrypted variants. PPK v3 supports Argon2d, Argon2i, and Argon2id through the pinned worker dependency.
- Unlock keys before starting the network connection timeout. A bad path, unsupported/malformed key, failed integrity check, or unsuccessful unlock stops with an error instead of silently falling back to password authentication. Supported conversions happen in memory; the selected file is not rewritten.
- Bound key files, derivation cost, worker concurrency, and decode time. Preserve responsiveness and release worker capacity on cancellation.
- Cancel pending username/passphrase prompts, authentication, and jump forwarding when a connection closes. Late replies cannot resume expired logins or save host-key trust after timeout or cancellation.
- Restore native group1 key exchange in Electron through a narrow version- and hash-checked patch to the pinned `ssh2` 1.17.0 dependency. Host signatures and normal host-fingerprint verification remain in place.

**Modern transport only** controls server host signatures, key exchange, ciphers, and MACs. User-key signature negotiation is separate. Automatic permits supported legacy algorithms when needed; it does not make them as strong as modern choices.

See the [SSH compatibility guide](../SSH_COMPATIBILITY.md) for setup, key formats, limits, and troubleshooting, and the [user guide](../USER_GUIDE.md#session-logging) for console logging.

## Supported scope

The Windows Electron runtime supports legacy RSA/SHA-1 host signatures, group1/group14 SHA-1 key exchange, AES-CBC/3DES-CBC, Blowfish/RC4, and supported legacy MACs. The offered algorithm list comes from the running SSH/crypto implementation, with modern choices ordered first in Automatic mode. RSA 1024-bit and 2048-bit identities are included in compatibility coverage; support for a legacy size is not a recommendation for new keys.

**Windows Electron does not support DSA (`ssh-dss`) host signatures or private-key authentication.** SSH 1, FIDO/security-key private-file formats, OpenSSH certificate authentication, and Ed448 are also unsupported. Format support does not guarantee every encryption/KDF combination or every device. Node.js source runs and the packaged Electron app can have different crypto capabilities.

An SSH audit observes one unauthenticated handshake, without credentials, commands, or host-trust decisions. It does not enumerate the server's full algorithm list. Private-key validation does not establish that the server authorizes the key or username.

Use **Update KonX** from installed 0.6.2 through 0.15.0 or portable 0.6.0 through 0.15.0. Installed 0.6.0/0.6.1 and version 0.5.0 or earlier need a manual upgrade; see [Updating KonX](../UPDATING.md).

## Validation

- **800/800 automated tests passed**, including real Electron logging-switch checks across all five layouts, real TCP text-file logging, login cancellation, and SSH host verification.
- **28/28 packaged SSH compatibility checks passed** using the shipped Windows runtime and application archive. Coverage includes modern and legacy negotiation, RSA 1024-bit host keys, SFTP, jump hosts, unauthenticated audits, successful rekey, changed-key rejection, and late trust replies.
- **16/16 private-key test groups passed** in the package verification run. Synthetic fixtures exercise the packaged worker, encrypted OpenSSH/PEM/PKCS#8/PPK files, all three PuTTY Argon2 variants, RSA/ECDSA/Ed25519 signed authentication, legacy RSA/SHA-1 login, and the explicit DSA runtime limitation.
- Windows installer and portable executables built successfully with the expected version metadata. **114 packaged source files**, **nine runtime dependencies**, and the exact SSH dependency patch were verified.
- Packaged unpacked and portable applications passed two-launch checks with isolated profiles. Real switch clicks produced the lit state and a text file containing the logging-on marker while excluding later logging-off output. Synthetic saved credentials, layout preferences, and cleared recent history survived restart.

The checks used source Node.js 24.13.0 and Electron 44.9.0 on Windows x64. Executables remain unsigned; an elevated installed upgrade was not performed for this release.

## Coverage

Compatibility verification uses synthetic keys, local SSH peers, and isolated application profiles. It does not establish compatibility with every device, key encryption scheme, SSH agent, or external authentication provider. Real network equipment and a complete installed upgrade with Windows elevation remain unverified for this release. Release checks do not change the user's installed copy or profile.

The six inherited AI, Wi-Fi, and security-assessment findings listed in [0.6.3](0.6.3.md#known-issues) remain unchanged.
